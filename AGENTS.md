# AGENTS.md

Guidelines for working on this codebase.

## Architecture: logic layer vs endpoints

- All functionality — validation, persistence, business rules and side effects (e.g. audio playback) — must live in the **logic layer**: internal, program-only functions (underscore-prefixed) that raise clear, exhaustive errors.
- **Endpoints** are only a filter between the outside world and the logic layer: they parse the incoming request, call a logic-layer function and map the result (or exception) to an HTTP response. No business logic belongs in endpoint handlers.

## Authorization

- Access is gated by a refresh-token cookie (`akupara-refresh`) issued on login through `/login`. It is a sliding cookie that resets every 15 minutes (max_age 900) on each authenticated response; it is never auto-issued on an unauthenticated request. Sessions are stored per-user server-side (`_SESSION_STORE`, token → `{username, admin, last_refresh}`), so multiple users can be logged in at the same time, each with their own cookie; every authenticated response renews only the requester's session. The cookie-auth decorators (`session_authenticated`, `api_key_or_admin_authenticated`) keep the same structure: they check the provided cookie is still valid (a live token **and** still within the sliding validity window, tracked server-side).
- A request without a valid refresh cookie gets no cookie in response. Instead:
  - **API requests** (`/api/*`) return **401** `{"error": "API key required."}`, so the GUI frontend detects it and redirects to `/login`.
  - **Page/asset requests** are redirected to `/login`.
- Login credentials come from `.env`: `USERNAME`/`PASSWORD` (legacy single user, a **non-admin** account since it carries no `admin` flag) and `USERS` (JSON list of `{"username", "password", "admin"}` for additional users, where `admin` is a boolean defaulting to `false` — a user is an admin **only** if `admin` is `true`); every `password` is the Argon2id encoded hash of the real password (fixed salt `akupara-salt`, `m=65536, t=2, p=1`). Usernames are matched case-insensitively. A `USERS` entry takes precedence over the legacy pair for the same username, so to grant admin, list the user in `USERS` with `"admin": true`. The password is hashed in the browser and the hash is compared server-side with a constant-time comparison. Endpoints that must only run for admin users (e.g. `/api/terminate`, `/api/restart`) are marked with `api_key_or_admin_authenticated`, which accepts a valid API key or a logged-in admin session.
- `admin_session_authenticated` is a stricter decorator for functionality/audio endpoints: it requires a logged-in **admin session cookie** (an API key is **not** accepted). A missing/invalid session returns **401** (so the frontend redirects to `/login`); a valid session that is not an admin returns **403** `{"error": "Admin privileges required."}` (so the frontend does not kick the logged-in user out). It is applied to `/api/audio`, `/api/audio/play`, `/api/shared-memory-enabled`, `/api/api-keys-enabled` and `/api/external-interactions-enabled` (their GET branches too — non-admin sessions get 403, so the toggles keep their server-rendered state) and, via the shared `_require_admin_session()` helper, to the mutating branch of `/api/settings`. The management endpoints (`/api/api-keys`, `/api/api-keys/<key>`, `/api/shared-memory`, `/api/shared-memory/<name>` PATCH/DELETE, `/api/network-access-ips`, `/api/network-access-ips/<ip>`) use `api_key_or_admin_authenticated` instead — they accept a valid API key **or** a logged-in admin session, so plugins can manage them remotely; their GET branches require it too (a non-admin session gets 401 and the frontend guards its fetches so non-admin users are not redirected to `/login`).
- The settings page is server-rendered with `is_admin`: non-admin users only see the General card (Account + Functionalities — now `API Keys`, `Internal Interactions` (was `Allow Discovery`), `External Interactions`), where the functionality toggles are rendered `disabled` (they can view the status but not change it); everything else (API Keys, Internal Interactions (was Shared Memory), External Interactions (was Network Interactions), Users, Customisation and the Terminate/Restart actions) is only rendered for admins. Users is now directly above Customisation (moved from above API Keys). The frontend only hashes passwords; every authorization check for changing passwords or settings lives in the backend. The admin-only UI fetches (`loadApiKeys`, `loadSharedMemory` (now internal interactions), `loadNetworkAccessIps`, `loadUsers`) are guarded in `ui/pages/index.html` so they no-op when their admin-only table is not rendered (non-admin sessions must not be 401-redirected to `/login`). The General card also shows the account `ROLE` with a `Log Out` button beside it (`<span id="accountRoleValue">` + `<button id="logoutBtn" data-tooltip="Log Out"><svg log-out></svg></button>`, `POST /api/logout` `session_authenticated` clears `akupara-refresh` cookie and `_SESSION_STORE`).
- `/login`, `/api/login`, `/ui/css/*`, `/ui/icons/*` (incl. `/ui/icons/akupara.svg`) and `/ui/js/argon2/argon2-bundled.min.js` are deliberately unauthenticated so the login page and its assets can be reached and served without a cookie. (Note: `/api/change-password` is a normal endpoint and is itself `session_authenticated`; it must be reached with a valid session cookie.)
- `/api/change-password` (`POST {current_password_hash, new_password_hash}`) changes the password of the logged-in account. Both hashes are computed client-side with Argon2id (same fixed salt as login). The server verifies the current hash against any stored hash for the username, then updates **every** configured record for that username (the legacy `PASSWORD` and/or the `password` field of the `USERS` entry), so all records stay in sync. A successful change plays the **success** sound and revokes every other live session of that account (`_revoke_other_sessions`, keeping only the session that made the change), so other logged-in sessions of the same account are logged out; a wrong current password plays the **error** sound (and returns 403, so the frontend does not redirect to `/login`). The General card UI (`wireAccountSection`) shows errors by keeping the offending input red and displaying a **red error tooltip** above it (via `showErrorTooltip`/`hideErrorTooltip`): a mismatch shows `Passwords do not match.` on the confirm input and a wrong current password shows `Current password is incorrect.` on the current-password input, each until the input is edited (editing hides the tooltip), and editing the Current Password field empties the New and Confirm fields (start-over reset).
- `/api/users` (network callable, `admin_session_authenticated`) handles **POST**, **GET**, **PATCH** and **DELETE**. **POST** `{username, password_hash, admin}` registers a new user by appending an entry to the `USERS` list in `.env` (`_register_user` in `src/main.py`): `password_hash` must be an Argon2id hash computed client-side (same salt/params as login) and `admin` a boolean (the Users card's two-segment control sends `"true"`/`"false"`); usernames must not contain the prohibited characters ` `, `,`, `;`, `\`, `/`, `:` or `%`, and must be **at least 8 characters long** — a too-short/prohibited username returns **400**, a duplicate username (against the `USERS` entries and the legacy `USERNAME`) returns **409**, success returns **201** and plays the **success** sound. **GET** returns `{"users": [{"username", "admin", "root"}]}` (sanitized by `_list_users` — password hashes are never returned, and the list is sorted root-first, then by admin, then by username). Each `USERS` entry carries a `root` boolean (only ever set in `.env` — it is not editable through the API; `_register_user` always creates `root: false` and no endpoint changes it, so there can only ever be as many roots as `.env` declares). The root user cannot lose admin status (`_set_user_admin` raises → **403**) nor be deleted (`_delete_user` raises → **403**), on top of the existing self-protection; the Users table renders the root row with a blue background and disables its admin segment and delete button for everyone, and the General card role indicator shows `Root` instead of `Admin` for the root account (`is_root` in the settings context). Renaming the root username is allowed only for the root account itself: a non-root admin renaming the root is rejected at the endpoint (**403**, checked with `_is_root_username` against the requester's session `root` — the logic layer has no session, so this authorization lives at the endpoint), and the UI disables the root row's edit button for non-root viewers (`currentSessionRoot`). **PATCH** `/api/users/<username>` renames (`{new_username}`) or toggles admin (`{admin}`); rename validates the same empty/prohibited/length rules (**400**), rejects duplicates (`UsernameTakenError` → **409**, with the target user excluded so re-saving the unchanged name succeeds and a no-op rename to the same name is allowed), plays the **acknowledge** sound (via the `@play_audio("acknowledge")` decorator, like other `.env` variable changes) and updates any matching live sessions (`_rename_session_username`); the admin toggle also plays the **acknowledge** sound and updates matching live sessions (`_set_session_admin`), so a renamed/demoted/promoted user's session immediately reflects the change. **DELETE** removes the `USERS` entry and plays the **success** sound; it also terminates every matching live session (`_delete_session_username`), so a deleted user is logged out (their next authenticated request returns 401 and the frontend redirects to `/login`). Deleting your own account or changing your own admin status returns **403** (and the UI disables those controls on your own row).
- The Users card of `ui/pages/settings.html` contains the registration form (username, password, confirm password, Standard/Admin segment, Register button) wired by `wireUserRegistration` in `ui/pages/index.html` (the confirm input is disabled until the password field is non-empty and editing the password field clears the confirm input), plus a table (`usersTable`) listing every `USERS` entry with a Standard/Admin segmented control, an in-place rename (like the API keys rename, pen→save icon, checks while typing **and** on save) and a delete (same fade/slide effect + sound). Errors are shown by keeping the offending input red and displaying a **red error tooltip** above it (via `showErrorTooltip`/`hideErrorTooltip`, used across the settings-page forms and the table renames); the tooltip's background matches the highlighted input's (`#fee2e2`) with dark-red text/border. The tooltip appears **live as the user types** (a duplicate/too-short username or duplicate name/IP shows its reason immediately via the `refresh*Invalid` validators) and also on submit: pressing Register with an empty/duplicate/too-short username shows the reason on the username input (e.g. `That username is already registered.`) until it is edited, a password mismatch shows `Passwords do not match.` on the confirm input until it is edited, and a rename save error keeps the rename input red with its reason until it is edited (typing in the input hides the tooltip when the value becomes valid); a successful registration just clears the form fields and refreshes the table via `loadUsers()`. The rows are server-rendered datasets (`users_json`, `has_users`, `current_username`, `legacy_username` — the last two feed the duplicate check so the legacy account's name is never taken) and the table data drives the client-side duplicate check (`isUsernameTaken` with an exclude-name for rename, so saving the unchanged name again is allowed).
- `/api/session` (network callable, `session_authenticated`) returns the current session's `{"username", "admin"}`. While the settings page is active the frontend polls it every 3 s (`syncSession`): if the logged-in user's **admin status changed** (promoted/demoted by another admin) the settings page is re-fetched (`loadPage('settings')`) so the server re-renders with the new role and the admin-only cards appear/disappear; if the **username changed** (renamed by another admin) the account summary and `currentUsername` are updated in place and the users table is refreshed.
- `/api/logout` (`POST {}` `session_authenticated`, `log_change`) clears the caller's `akupara-refresh` session (`_SESSION_STORE.pop(token)` + `delete_cookie`) and returns `200 {"status":"ok"}`. The General card shows it as a `Log Out` button beside the `ROLE` pill (`<span id="accountRoleValue">` + `<button id="logoutBtn" data-tooltip="Log Out"><svg log-out></svg></button>`, lucide `log-out` icon `m16 17 5-5-5-5/M21 12H9/M9 21H5…`, `wireLogout` in `ui/pages/index.html` `fetchWithHandshake('/api/logout',{method:'POST'})` → `window.location.href='/login'`).
- All create/update operations get the same double-level duplicate protection (UI + endpoint + logic layer), each keyed on the entity's name: API keys are keyed on the API key **name** (`_create_api_key`/`_rename_api_key` raise `DuplicateNameError` → **409**; the frontend checks `isApiKeyNameTaken`, also during rename with an exclude-key), shared variables on the variable **name** (`_create_shared_variable` raises `DuplicateNameError` → **409**; frontend `isSharedVariableNameTaken`), network access IPs on the canonical **IP** (deduped in `_set_network_access_ip`; frontend `isNetworkAccessIpDuplicate`), and users on the **username** (`_register_user`/`_rename_user` raise `UsernameTakenError` → **409**; frontend `isUsernameTaken`, also during rename with an exclude-name). Everywhere, the prohibited characters `[ ,;\\/:%]` are enforced (backend `_FORBIDDEN_KEY_NAME_CHARS` = `set(" ,;:\\/%")`, reused by `_is_valid_key_name`, plus frontend regexes). Shared-variable **values** are validated per type in all three layers: `_normalize_shared_value` (backend), the endpoints (ValueError → **400**), and `parseSharedValueInput`/`serializeSharedValue` (frontend, in both the add and edit flows).
- A successful login plays the **success** sound; a failed login (wrong password, HTTP 401) plays the **error** sound.
- Every user and API key carries a secret `id` (a hash, set in `.env` only, never changed, never exposed to the UI and never returned by any endpoint): user ids live in the `USERS` entries (`_register_user` generates one with `secrets.token_hex(16)`; `_load_users` keeps them internal), and API key ids are the SHA-256 hash of the key, stored in `API_KEYS` as `name:key:id` (`_api_key_id`, so the key is never logged plaintext). The ids exist so the change logs can attribute a change to a stable actor even though usernames can change. The `@log_change` decorator marks an endpoint as a change: after a successful (2xx) `POST`/`PATCH`/`DELETE` it logs `Change recorded: user <id> -> <method> <path> (<status>)` or `Change recorded: api-key <id> -> ...`, resolving the actor with `_resolve_actor()` (from the session or the `X-Api-Key` header). It is applied to every authenticated mutation endpoint (`/api/settings`, `/api/audio`, `/api/audio/play`, the `-enabled` toggles, `/api/api-keys`, `/api/api-keys/<key>`, `/api/shared-memory`, `/api/shared-memory/<name>`, `/api/network-access-ips`, `/api/network-access-ips/<ip>`, `/api/change-password`, `/api/users`, `/api/users/<username>`, `/api/terminate`, `/api/restart`). The ids never reach the UI: `_list_users` and `_list_api_keys` strip them.

## Audio

- Every `.env` variable change — including one where the saved value does not actually change — plays the **acknowledge** sound. The corresponding logic-layer functions are marked with the `@play_audio("acknowledge")` decorator.
- Exception: changing `PLAY_AUDIOS` or `DISPLAY_PROMOTION` produces no sound.
- Exception: user creation (`_register_user`) and deletion (`_delete_user`) play the **success** sound (played explicitly at the end), not the acknowledge sound; user username/status changes (`_rename_user`, `_set_user_admin`) play the **acknowledge** sound like other `.env` variable changes.
- Exception: a password change (`/api/change-password`) plays the **success** sound on success and the **error** sound on a wrong current password, not the acknowledge sound.

## Workers

- A worker is a class whose two public methods are named `start()` and `stop()`, following the audio-worker naming standard (see `AudioOrchestrator` in `src/audio.py` and `ExternalAccessWorker` in `src/network.py`).
- `start()` begins the worker and `stop()` shuts it down; both are idempotent.
- For the audio worker, `AudioOrchestrator.start()`/`stop()` only toggle its enabled state (driven by `PLAY_AUDIOS`); the actual playback sub-workers are started on demand via `play()`. For the network worker, `ExternalAccessWorker.start()`/`stop()` drive its own lifecycle directly (it has no sub-workers).
- Logic-layer setters toggle a worker by calling its `start()`/`stop()` when the associated `.env` flag changes (e.g. `_set_external_access` and the master switch `_set_external_interactions` → `_start_external_access_worker` / `_stop_external_access_worker`).
- The endpoints and methods the network worker may run are marked with `@network.network_worker_callable`; together they are the only ones the network worker serves — any other request is answered with a 404 byte-identical to a non-existent endpoint. The marker is orthogonal to the auth decorators: marked endpoints still run their auth stack, so a remote client must authenticate (log in via `/api/login` to get a session, or present a valid API key) and is then subject to the same authorization as a local client. `/api/settings` is intentionally **not** network callable.
- The network worker also gates requests by remote IP (`_network_worker_ip_policy` in `src/main.py`): each IP in `NETWORK_ACCESS_IPS` carries one of the string values `"allow"`, `"unknown"` or `"block"`. Requests from `"allow"` IPs pass through and `"block"` IPs are refused. New IPs are always recorded in the list with `"unknown"`, regardless of the policy for new IPs; requests from `"unknown"` IPs and from IPs not yet in the list are decided by `NETWORK_ACCESS_ALLOW_NEW`. These automatic recordings play the **acknowledge** sound.
- External access is a sub-feature of the network-interactions functionality, controlled by the General card's **External Interactions** toggle (the master switch, wired to `/api/external-interactions-enabled`, `admin_session_authenticated`): toggling it **on** enables both `NETWORK_INTERACTIONS` and `EXTERNAL_ACCESS` and starts the worker; toggling it **off** stops the worker and disables both (`_set_external_interactions`). The master state is `NETWORK_INTERACTIONS and EXTERNAL_ACCESS` (`_external_interactions_enabled`), used to render the toggle and the External Interactions card (was `Network Interactions`, now `External Interactions`, icon `radio` was `radio-tower` (was `globe`)). On startup the external-access worker (`ExternalAccessWorker` in `src/network.py`) starts when `EXTERNAL_ACCESS=true`, binding the app to the first non-loopback IPv4 device address on the same `SERVICE_PORT`, in parallel with the loopback-only main server. The External Interactions card shows the bind address only while the worker is actually running (`_external_access_worker is not None` in `_network_worker_bind_address`); when it is not running the address renders as `Disabled`. Clients connecting from outside must be allowed by the IP policy (`allow`, or `NETWORK_ACCESS_ALLOW_NEW=true`), and Windows Firewall must permit the Python process inbound on the network profile. The former `Shared Memory` card is now `Internal Interactions` (icon `messages-square` was `database`/`ellipse`, id `discoveryCard` → `internalInteractionsCard`), visibility tied to `INTERNAL_INTERACTIONS` (was `ALLOW_DISCOVERY`, now removed).

## Plugins — list & library

- The **plugins-lib** folder is `resources/plugins-lib/`. Its catalog is split into **hash-range files** named `<low>-<high>.json` (64-char hex bounds, e.g. `000…-fff….json` while small). Each file holds a JSON **list** of plugin objects. A plugin has exactly `{"hash","name","description","repo","trust_mark"}` — no `reverse_index_keys` stored there and no duplication (`trust_hash` is legacy, read with fallback in `src/plugin_bridge.py:_get_trust_signature`, never written). `hash` is the ID, generated on insert as `SHA-256("name|description|repo|timestamp")` (`timestamp` is ISO-8601 UTC, `scripts/manage_plugin_library.py:generate_id_hash`).
- `reverse-index.json` is the **apposite file** `word -> [hash, …]` (lower-cased keys, `word` is `\w+` token for the research query). It is the *only* place `reverse_index_keys` live; hash-range entries never store them — `keys_for_hash(hash)` (`scripts/manage_plugin_library.py:keys_for_hash` / `src/plugin_bridge.py:_keys_for_hash`) computes them live from `reverse-index.json`.
- **Search** (`src/plugin_bridge.py:_search_plugins`, endpoint `POST /api/plugins/search`) tokenises the regex into `\w+` tokens, unions hashes from `reverse-index.json`, then regex-filters those candidates (case-insensitive on `name/description/repo` + JSON dump). If the index misses, it falls back to a full catalog regex scan. `reverse-index.json` therefore optimises research but does not change its semantics.
- **Folder integrity hash:** at any change, every file in `resources/plugins-lib/` *except* the apposite `hash` file (`resources/plugins-lib/hash`) is hashed individually (`SHA-256` hex), sorted by filename, concatenated and hashed again (`SHA-256`). Result is stored in `hash` (`scripts/manage_plugin_library.py:compute_plugins_lib_hash` / `src/plugin_bridge.py:_compute_plugins_lib_hash`). The public GPG key `resources/plugins-lib/lorenbll-akupara-pub` lives inside `plugins-lib` so it is hashed too. Splitting the library (`manage_plugin_library.py:action_split`) redistributes plugins into `n` equal hex intervals and rewrites all range files sorted by `hash`, then recomputes `hash`.
- **Loader startup** (`src/plugin_bridge.py:PluginBridge.start`, called immediately in `src/main.py:get_plugin_bridge().start()` after `_initialize_service_config`): (1) compares local `hash` file with remote GitHub latest `https://raw.githubusercontent.com/LorenBll/Akupara/main/resources/plugins-lib/hash` — mismatch → `log_error` + `warn` sound and `is_started` stays `False` (offline → `log_warn` and continues); (2) recomputes folder hash and checks against local `hash` — mismatch (illicit interaction) → `log_error` + `error` sound and stays stopped. On success → `log_info Plugin loader started` and `is_started` true. Follows worker `start()/stop()` idempotency.
- **GPG prerequisite:** `gpg` (`GnuPG`, `C:\Program Files\GnuPG\bin` on Windows) must be on `PATH` for trust operations — signing (`gpg --armor --detach-sign`) and verification (`gpg --verify`).

## Trustworthiness mark

- For a plugin with `hash H`, the **trust data** is canonical JSON `{"hash":H,"name":…,"description":…,"repo":…,"reverse_index_keys":[…sorted]}` (`scripts/manage_plugin_library.py:build_trust_data` / `src/plugin_bridge.py:_build_trust_data` — `reverse_index_keys` computed live, never persisted). Canonicalisation is `json.dumps(sort_keys=True, separators=(",",":"))`.
- The Akupara developer signs that JSON with their **private GPG key** (`gpg --armor --detach-sign`). If `gpg` is unavailable, a deterministic `SHA-256` hex fallback is stored (warn).
- **Stored as single field** `trust_mark: string` (armored `-----BEGIN PGP SIGNATURE-----…` or `""` when absent) in the hash-range entry — no `trust_hash` duplication, no `reverse_index_keys` duplication. Legacy `trust_hash` (`{"data":…,"signature":…}` or string) is only read for backward compat (`_get_trust_signature`).
- **Public key** `resources/plugins-lib/lorenbll-akupara-pub` (armored) is distributed *inside* `plugins-lib` so it is covered by the folder hash. The private key is never committed.
- **Verification** (`src/plugin_bridge.py:verify_plugin_signature`): rebuilds trust data (including live `reverse_index_keys`), then if `trust_mark` is 64-hex → compares `SHA-256(canonical)`; else imports public key if needed and runs `gpg --verify sig data` (tries `gpg`, `C:\Program Files\GnuPG\bin\gpg.exe`). `""` / missing → `False`; tampered `name/description/repo/keys` → `False`. No piece of the signature is ever displayed by the manager (`scripts/manage_plugin_library.py:_print_plugin_card` shows only `[present]/[absent]`).

## Files that must not be committed

- `scripts/manage_plugin_library.py` — developer-only helper (insert/list/delete/update/split, GPG signing, hashing, `repo_exists` HTTP check). Runs via `scripts/manage_plugin_library.bat` / `.sh` wrappers (also not committed).
- `scripts/manage_plugin_library.bat` and `scripts/manage_plugin_library.sh` — functionally equivalent launchers (`python`/`python3` `3.10+` check, `.venv` create/activate, `pip install -r requirements.txt`, `exec python scripts/manage_plugin_library.py "$@"`).
- Private GPG key material (local keyring files, backups and any `*secret*.asc`) and `.env` (contains `PASSWORD`/`USERS`/`API_KEYS` hashes). Public key `resources/plugins-lib/lorenbll-akupara-pub` **is** committed (hashed).
