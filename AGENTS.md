# AGENTS.md

Guidelines for working on this codebase.

## Architecture: logic layer vs endpoints

- All functionality — validation, persistence, business rules and side effects (e.g. audio playback) — must live in the **logic layer**: internal, program-only functions (underscore-prefixed) that raise clear, exhaustive errors.
- **Endpoints** are only a filter between the outside world and the logic layer: they parse the incoming request, call a logic-layer function and map the result (or exception) to an HTTP response. No business logic belongs in endpoint handlers.

## Authorization

- Access is gated by a refresh-token cookie (`akupara-refresh`) issued on login through `/login`. It is a sliding cookie that resets every 15 minutes (max_age 900) on each authenticated response; it is never auto-issued on an unauthenticated request. Sessions are stored per-user server-side (`_SESSION_STORE`, token → `{username, admin, last_refresh}`), so multiple users can be logged in at the same time, each with their own cookie; every authenticated response renews only the requester's session. The cookie-auth decorators (`session_authenticated`, `api_key_or_admin_authenticated`) keep the same structure: they check the provided cookie is still valid (a live token **and** still within the sliding validity window, tracked server-side).
- A request without a valid refresh cookie gets no cookie in response. Instead:
  - **API requests** (`/api/*`) return **401** `{"error": "API key required."}`, so the GUI frontend detects it and redirects to `/login`.
  - **Page/asset requests** are redirected to `/login`.
- Login credentials come from `.env`: `USERS` (JSON list of `{"username", "password", "admin"}` for additional users, where `admin` is a boolean defaulting to `false` — a user is an admin **only** if `admin` is `true`); every `password` is the Argon2id encoded hash of the real password (fixed salt `akupara-salt`, `m=65536, t=2, p=1`). Usernames are matched case-insensitively. To grant admin, list the user in `USERS` with `"admin": true`. The password is hashed in the browser and the hash is compared server-side with a constant-time comparison. Endpoints that must only run for admin users (e.g. `/api/terminate`, `/api/restart`) are marked with `api_key_or_admin_authenticated`, which accepts a valid API key or a logged-in admin session.
- `admin_session_authenticated` is a stricter decorator for functionality/audio endpoints: it requires a logged-in **admin session cookie** (an API key is **not** accepted). A missing/invalid session returns **401** (so the frontend redirects to `/login`); a valid session that is not an admin returns **403** `{"error": "Admin privileges required."}` (so the frontend does not kick the logged-in user out). It is applied to `/api/audio`, `/api/audio/play`, `/api/shared-memory-enabled`, `/api/api-keys-enabled` and `/api/external-interactions-enabled` (their GET branches too — non-admin sessions get 403, so the toggles keep their server-rendered state), to the external-interactions firewall endpoints (`/api/external-interactions-incoming-ips`, `/api/external-interactions-outgoing-ips` and their `<ip>` items, `/api/external-interactions-allow-new`, `/api/external-interactions-allow-new-outgoing`), and, via the shared `_require_admin_session()` helper, to the mutating branch of `/api/settings`. The management endpoints (`/api/api-keys`, `/api/api-keys/<key>`, `/api/shared-memory`, `/api/shared-memory/<name>` PATCH/DELETE) use `api_key_or_admin_authenticated` instead — they accept a valid API key **or** a logged-in admin session, so plugins can manage them remotely; their GET branches require it too (a non-admin session gets 401 and the frontend guards its fetches so non-admin users are not redirected to `/login`).
- The settings page is server-rendered with `is_admin`: non-admin users only see the General card (Account + Functionalities — now `API Keys`, `Internal Interactions` (was `Allow Discovery`), `External Interactions`), where the functionality toggles are rendered `disabled` (they can view the status but not change it); everything else (API Keys, Internal Interactions (was Shared Memory), External Interactions (was Network Interactions), Users, Customisation and the Terminate/Restart actions) is only rendered for admins. Users is now directly above Customisation (moved from above API Keys). The frontend only hashes passwords; every authorization check for changing passwords or settings lives in the backend. The admin-only UI fetches (`loadApiKeys`, `loadSharedMemory` (now internal interactions), `loadExternalInteractionsIps`, `loadUsers`) are guarded in `ui/pages/index.html` so they no-op when their admin-only table is not rendered (non-admin sessions must not be 401-redirected to `/login`). The General card also shows the account `ROLE` with a `Log Out` button beside it (`<span id="accountRoleValue">` + `<button id="logoutBtn" data-tooltip="Log Out"><svg log-out></svg></button>`, `POST /api/logout` `session_authenticated` clears `akupara-refresh` cookie and `_SESSION_STORE`).
- `/login`, `/api/login`, `/ui/css/*`, `/ui/icons/*` (incl. `/ui/icons/akupara.svg`) and `/ui/js/argon2/argon2-bundled.min.js` are deliberately unauthenticated so the login page and its assets can be reached and served without a cookie. (Note: `/api/change-password` is a normal endpoint and is itself `session_authenticated`; it must be reached with a valid session cookie.)
- `/api/change-password` (`POST {current_password_hash, new_password_hash}`) changes the password of the logged-in account. Both hashes are computed client-side with Argon2id (same fixed salt as login). The server verifies the current hash against any stored hash for the username, then updates **every** configured record for that username so all records stay in sync. A successful change plays the **success** sound and revokes every other live session of that account (`_revoke_other_sessions`, keeping only the session that made the change), so other logged-in sessions of the same account are logged out; a wrong current password plays the **error** sound (and returns 403, so the frontend does not redirect to `/login`). The General card UI (`wireAccountSection`) shows errors by keeping the offending input red and displaying a **red error tooltip** above it (via `showErrorTooltip`/`hideErrorTooltip`): a mismatch shows `Passwords do not match.` on the confirm input and a wrong current password shows `Current password is incorrect.` on the current-password input, each until the input is edited (editing hides the tooltip), and editing the Current Password field empties the New and Confirm fields (start-over reset).
- `/api/users` (network callable, `admin_session_authenticated`) handles **POST**, **GET**, **PATCH** and **DELETE**. **POST** `{username, password_hash, admin}` registers a new user by appending an entry to the `USERS` list in `.env` (`_register_user` in `src/main.py`): `password_hash` must be an Argon2id hash computed client-side (same salt/params as login) and `admin` a boolean (the Users card's two-segment control sends `"true"`/`"false"`); usernames must not contain the prohibited characters ` `, `,`, `;`, `\`, `/`, `:` or `%`, and must be **at least 8 characters long** — a too-short/prohibited username returns **400**, a duplicate username (against the `USERS` entries) returns **409**, success returns **201** and plays the **success** sound. **GET** returns `{"users": [{"username", "admin", "root"}]}` (sanitized by `_list_users` — password hashes are never returned, and the list is sorted root-first, then by admin, then by username). Each `USERS` entry carries a `root` boolean (only ever set in `.env` — it is not editable through the API; `_register_user` always creates `root: false` and no endpoint changes it, so there can only ever be as many roots as `.env` declares). The root user cannot lose admin status (`_set_user_admin` raises → **403**) nor be deleted (`_delete_user` raises → **403**), on top of the existing self-protection; the Users table renders the root row with a blue background and disables its admin segment and delete button for everyone, and the General card role indicator shows `Root` instead of `Admin` for the root account (`is_root` in the settings context). Renaming the root username is allowed only for the root account itself: a non-root admin renaming the root is rejected at the endpoint (**403**, checked with `_is_root_username` against the requester's session `root` — the logic layer has no session, so this authorization lives at the endpoint), and the UI disables the root row's edit button for non-root viewers (`currentSessionRoot`). **PATCH** `/api/users/<username>` renames (`{new_username}`) or toggles admin (`{admin}`); rename validates the same empty/prohibited/length rules (**400**), rejects duplicates (`UsernameTakenError` → **409**, with the target user excluded so re-saving the unchanged name succeeds and a no-op rename to the same name is allowed), plays the **acknowledge** sound (via the `@play_audio("acknowledge")` decorator, like other `.env` variable changes) and updates any matching live sessions (`_rename_session_username`); the admin toggle also plays the **acknowledge** sound and updates matching live sessions (`_set_session_admin`), so a renamed/demoted/promoted user's session immediately reflects the change. **DELETE** removes the `USERS` entry and plays the **success** sound; it also terminates every matching live session (`_delete_session_username`), so a deleted user is logged out (their next authenticated request returns 401 and the frontend redirects to `/login`). Deleting your own account or changing your own admin status returns **403** (and the UI disables those controls on your own row).
- The Users card of `ui/pages/settings.html` contains the registration form (username, password, confirm password, Standard/Admin segment, Register button) wired by `wireUserRegistration` in `ui/pages/index.html` (the confirm input is disabled until the password field is non-empty and editing the password field clears the confirm input), plus a table (`usersTable`) listing every `USERS` entry with a Standard/Admin segmented control, an in-place rename (like the API keys rename, pen→save icon, checks while typing **and** on save) and a delete (same fade/slide effect + sound). Errors are shown by keeping the offending input red and displaying a **red error tooltip** above it (via `showErrorTooltip`/`hideErrorTooltip`, used across the settings-page forms and the table renames); the tooltip's background matches the highlighted input's (`#fee2e2`) with dark-red text/border. The tooltip appears **live as the user types** (a duplicate/too-short username or duplicate name/IP shows its reason immediately via the `refresh*Invalid` validators) and also on submit: pressing Register with an empty/duplicate/too-short username shows the reason on the username input (e.g. `That username is already registered.`) until it is edited, a password mismatch shows `Passwords do not match.` on the confirm input until it is edited, and a rename save error keeps the rename input red with its reason until it is edited (typing in the input hides the tooltip when the value becomes valid); a successful registration just clears the form fields and refreshes the table via `loadUsers()`. The rows are server-rendered datasets (`users_json`, `has_users`, `current_username`) and the table data drives the client-side duplicate check (`isUsernameTaken` with an exclude-name for rename, so saving the unchanged name again is allowed).
- `/api/session` (network callable, `session_authenticated`) returns the current session's `{"username", "admin"}`. While the settings page is active the frontend polls it every 3 s (`syncSession`): if the logged-in user's **admin status changed** (promoted/demoted by another admin) the settings page is re-fetched (`loadPage('settings')`) so the server re-renders with the new role and the admin-only cards appear/disappear; if the **username changed** (renamed by another admin) the account summary and `currentUsername` are updated in place and the users table is refreshed.
- `/api/logout` (`POST {}` `session_authenticated`, `log_change`) clears the caller's `akupara-refresh` session (`_SESSION_STORE.pop(token)` + `delete_cookie`) and returns `200 {"status":"ok"}`. The General card shows it as a `Log Out` button beside the `ROLE` pill (`<span id="accountRoleValue">` + `<button id="logoutBtn" data-tooltip="Log Out"><svg log-out></svg></button>`, lucide `log-out` icon `m16 17 5-5-5-5/M21 12H9/M9 21H5…`, `wireLogout` in `ui/pages/index.html` `fetchWithHandshake('/api/logout',{method:'POST'})` → `window.location.href='/login'`).
- All create/update operations get the same double-level duplicate protection (UI + endpoint + logic layer), each keyed on the entity's name: API keys are keyed on the API key **name** (`_create_api_key`/`_rename_api_key` raise `DuplicateNameError` → **409**; the frontend checks `isApiKeyNameTaken`, also during rename with an exclude-key), shared variables on the variable **name** (`_create_shared_variable` raises `DuplicateNameError` → **409**; frontend `isSharedVariableNameTaken`), external interactions IPs on the canonical **IP** per direction (deduped on rename in `_update_external_interactions_entry` → **409**; frontend `isFirewallIpDuplicate`), and users on the **username** (`_register_user`/`_rename_user` raise `UsernameTakenError` → **409**; frontend `isUsernameTaken`, also during rename with an exclude-name). Everywhere, the prohibited characters `[ ,;\\/:%]` are enforced (backend `_FORBIDDEN_KEY_NAME_CHARS` = `set(" ,;:\\/%")`, reused by `_is_valid_key_name`, plus frontend regexes). Shared-variable **values** are validated per type in all three layers: `_normalize_shared_value` (backend), the endpoints (ValueError → **400**), and `parseSharedValueInput`/`serializeSharedValue` (frontend, in both the add and edit flows).
- A successful login plays the **success** sound and resets the consecutive failed-login counter; a failed login (wrong password, HTTP 401) plays the **warn** sound only for the first 3 consecutive failures — further failures stay silent (no decorator sound and no log sound via `silent=True`) until a success resets the counter (`_register_failed_login_attempt` / `_reset_failed_login_attempts` in `src/main.py`).
- Every user and API key carries a secret `id` (a random token, set in `.env` only, never changed, never exposed to the UI and never returned by any endpoint): user ids live in the `USERS` entries (`_register_user` generates one with `secrets.token_hex(16)`; `_load_users` keeps them internal), and API key ids are generated with `secrets.token_hex(16)` the same way (`_api_key_id`), stored in the `API_KEYS` JSON entries as `{"name", "key", "id"}` (so the key is never logged plaintext). The ids exist so the change logs can attribute a change to a stable actor even though usernames can change. The `@log_change` decorator marks an endpoint as a change: after a successful (2xx) `POST`/`PATCH`/`DELETE` it logs `Change recorded: user <id> -> <method> <path> (<status>)` or `Change recorded: api-key <id> -> ...`, resolving the actor with `_resolve_actor()` (from the session or the `X-Api-Key` header). It is applied to every authenticated mutation endpoint (`/api/settings`, `/api/audio`, `/api/audio/play`, the `-enabled` toggles, `/api/api-keys`, `/api/api-keys/<key>`, `/api/shared-memory`, `/api/shared-memory/<name>`, the external-interactions firewall endpoints, `/api/change-password`, `/api/users`, `/api/users/<username>`, `/api/terminate`, `/api/restart`). The ids never reach the UI: `_list_users` and `_list_api_keys` strip them.

## Audio

- Every `.env` variable change — including one where the saved value does not actually change — plays the **acknowledge** sound. The corresponding logic-layer functions are marked with the `@play_audio("acknowledge")` decorator.
- Exception: changing `PLAY_AUDIOS` or `DISPLAY_PROMOTION` produces no sound.
- Exception: user creation (`_register_user`) and deletion (`_delete_user`) play the **success** sound (played explicitly at the end), not the acknowledge sound; user username/status changes (`_rename_user`, `_set_user_admin`) play the **acknowledge** sound like other `.env` variable changes.
- Exception: a password change (`/api/change-password`) plays the **success** sound on success and the **error** sound on a wrong current password, not the acknowledge sound.
- The **startup sound** is fixed to `resources/audios/logo-reveal.wav` (not customisable) and plays once after every loading operation at startup, only when both `PLAY_AUDIOS` and `PLAY_STARTUP_SOUND` (`.env`, default `true`) are on. It is toggled from the Customisation card's `Play Startup Sound` slider (`ui/pages/settings.html#playStartupSoundRow` / `#playStartupSoundToggle`, above `Play Log Sounds`), wired to `/api/startup-sound-enabled` (`GET`/`POST {playStartupSound: bool}`, `admin_session_authenticated`, gated by `_require_play_audios_enabled()` → **403** when `PLAY_AUDIOS` is off). The row renders `sound-row-disabled` with the toggle `disabled` when `PLAY_AUDIOS` is off (`updatePlayAudios` keeps it in sync). Changing it plays the **acknowledge** sound (`_set_play_startup_sound`).

## Workers

- A worker is a class whose two public methods are named `start()` and `stop()`, following the audio-worker naming standard (see `AudioOrchestrator` in `src/audio.py` and `ExternalInteractionsWorker` in `src/network.py`).
- `start()` begins the worker and `stop()` shuts it down; both are idempotent.
- For the audio worker, `AudioOrchestrator.start()`/`stop()` only toggle its enabled state (driven by `PLAY_AUDIOS`); the actual playback sub-workers are started on demand via `play()`. For the external interactions worker, `ExternalInteractionsWorker.start()`/`stop()` drive its own lifecycle directly (it has no sub-workers).
- Logic-layer setters toggle a worker by calling its `start()`/`stop()` when the associated `.env` flag changes (e.g. `_set_external_interactions` and the master switch `_set_external_interactions` → `_start_external_interactions_worker` / `_stop_external_interactions_worker`).
- The endpoints and methods the external interactions worker may run are marked with `@network.external_interactions_callable`; together they are the only ones the external interactions worker serves — any other request is answered with a 404 byte-identical to a non-existent endpoint. The marker is orthogonal to the auth decorators: marked endpoints still run their auth stack, so a remote client must authenticate (log in via `/api/login` to get a session, or present a valid API key) and is then subject to the same authorization as a local client. `/api/settings` is intentionally **not** network callable.
- The network worker gates requests by remote IP (`_external_interactions_worker_ip_policy` in `src/main.py`) against the **incoming** list (`EXTERNAL_INTERACTIONS_INCOMING_IPS`): each entry is `{"ip", "plugins", "action", "Note"}` where `action` is one of the string values `"allow"`, `"unknown"` or `"block"` and `plugins` is a list of plugin names (`"akupara"` blocks the IP from the Akupara workers, and therefore from all plugins). Requests from `"allow"` IPs pass through and `"block"` IPs are refused. New IPs are always recorded in the incoming list with `"unknown"` scoped to `["akupara"]`, regardless of the policy for new IPs; requests from `"unknown"` IPs and from IPs not yet in the list are decided by `EXTERNAL_INTERACTIONS_ALLOW_NEW`. These automatic recordings play the **acknowledge** sound. A parallel **outgoing** list (`EXTERNAL_INTERACTIONS_OUTGOING_IPS`, same entry shape) with its own default (`EXTERNAL_INTERACTIONS_ALLOW_NEW_OUTGOING`) exists for outgoing requests. Tag clouds (`plugins` lists) are always sorted alphabetically with `akupara` first, both in `.env` (on save/load) and in the UI, where the `akupara` tag renders in a different colour (`.event-plugin-tag-akupara`). The card has `Incoming Interactions` (policy toggle, table) and `Outgoing Interactions` (default-policy toggle, table with IP and tag cloud swapped) sections; tables support row edit mode (pen button turns the IP into a text box; the note cell can then also be opened for editing and both are saved together via `Save Changes`), tag `×` removal (`PATCH {remove_plugin}` drops the plugin from the entry's list and cell), drag-move of a tag across cells of the same table (`PATCH {add_plugin}` on the target then `{remove_plugin}` on the source; source gap and drop gap shown as dashed placeholders in distinct colours, the drop gap positioned where the tag will actually end up after cloud sorting; cancelled on its own cell, on the other table, or when already present), policy segment clicks and delete with the standard row-deletion animation — there is no insert flow. All card endpoints are `external_interactions_worker_callable` + `admin_session_authenticated`.
- External Interactions is the master external-interaction feature, controlled by the General card's **External Interactions** toggle, wired to `/api/external-interactions-enabled` and `admin_session_authenticated`. Toggling it **on** enables the external-interaction functionality and starts the worker; toggling it **off** stops the worker and disables the functionality (`_set_external_interactions`). The master state is `_external_interactions_enabled`, used to render the toggle and the **External Interactions** card (formerly `External Interactions`; icon `radio`, formerly `radio-tower`/`globe`). The former `NETWORK_INTERACTIONS` concept is no longer a separate project feature or user-facing state and should be treated as removed/collapsed into External Interactions. On startup, `ExternalInteractionsWorker` in `src/network.py` starts when external interactions are enabled, binding the app to the first non-loopback IPv4 device address on the same `SERVICE_PORT`, in parallel with the loopback-only main server. The External Interactions card shows the bind address only while the worker is actually running (`_external_interactions_worker is not None` in `_external_interactions_worker_bind_address`); otherwise the address renders as `Disabled`. Clients connecting from outside must be allowed by the IP policy (`allow`, or `EXTERNAL_INTERACTIONS_ALLOW_NEW=true`), and Windows Firewall must permit the Python process inbound on the network profile. The former `Shared Memory` card is now **Internal Interactions** (icon `messages-square`, formerly `database`/`ellipse`; id `discoveryCard` → `internalInteractionsCard`). Its visibility is tied to `INTERNAL_INTERACTIONS`; the former `ALLOW_DISCOVERY` setting has been removed. There is no separate External Interactions feature, toggle, card, master state, or configuration concept. References to network interactions should be migrated to External Interactions or the appropriate lower-level implementation detail (`ExternalInteractionsWorker`, IP policy, etc.) and then removed.


## Disabled Interactive Elements

- Every element which is disabled and, when not disabled, could be interacted with (buttons, sliders/toggles, input boxes, segmented controls, dropdowns, etc.) must appear disabled: `cursor: not-allowed` and visually dimmed (`opacity: 0.45-0.55` and `cursor: not-allowed` via `:disabled` or `.disabled` rules in `ui/css/index.css`). This applies to `button:disabled`, `input:disabled`, `select:disabled`, `.toggle:disabled`, `.generate-api-key-btn:disabled`, `.api-key-name-input:disabled`, `.external-interaction-segment:disabled`, `.sound-select:disabled`, `.icon-btn:disabled`, `.pill-action-btn:disabled`, etc. The rule is enforced at startup by `src/main.py:_verify_disabled_styles` (reads `ui/css/index.css` and verifies every `:disabled` interactive rule contains `cursor: not-allowed`) and in CI by `.github/workflows/disabled-styles.yml`.

## Project hash & updates

- The **project hash** is the repo-root `hash` file, now stored **signed** (hash hex + armored PGP signature). It is generated **manually** by the developer via `scripts/administration.py` (Project → Compute project hash) — there is no CI workflow that computes it on push. The algorithm: every non-excluded tracked file is hashed individually (`SHA-256` hex, text files normalised CRLF→LF), sorted by relative path, concatenated and hashed again. Excluded: the `hash` file itself, `resources/configuration.json` (installation-specific), `resources/plugins-lib/` (the plugin library has its own hash), `resources/audios/` (audio changes must not affect the project hash), `.git`, `.venv`/`venv`/`ENV`/`env`, `.vscode`, `.idea`, `logs`, `__pycache__`, `.pytest_cache`, `htmlcov`, `dist`, `build`, `.github/__pycache__`, `*.egg-info`, `*.pyc`/`*.pyo`, `*.so`. At startup the runtime verifies the stored hash's signature (public key `resources/plugins-lib/lorenbll-akupara-pub`) before comparing effective vs indicated — invalid signature → crash; mismatch → crash unless development mode. On a release the `hash` file is uploaded as a release asset (`gh release upload <tag> hash --clobber`), so the unsigned hash of the released tree is available at `https://github.com/LorenBll/Akupara/releases/latest/download/hash`.
- **Local integrity check** (`src/main.py:_compute_local_project_hash` / `_verify_local_project_integrity`, run at every startup): recomputes the project hash from the tracked files (`git ls-files`, same exclusions as CI — including `resources/plugins-lib/`, which has its own hash, and `resources/audios/` — text files normalised CRLF→LF so a Windows checkout hashes identically to the Linux CI checkout) and compares it with the stored `hash` file — mismatch (illicit interaction or partial install) → `log_error`; failure to enumerate the tracked file list (e.g. not a git checkout) is also a failure → `log_error`.
- **Version display** (`ui/pages/settings.html` Version section in General and Plugins cards): shows `Effective Version` (latest computed hash — `_get_effective_project_version` / `_get_effective_plugins_lib_version` via `_compute_local_project_hash` / `plugin_bridge._compute_plugins_lib_hash`) and `Indicated Version` (hash file — `_get_indicated_project_version` / `_get_indicated_plugins_lib_version` via `_get_local_project_hash` / `plugin_bridge._read_stored_hash`) side by side (`effectiveVersionDisplay`/`indicatedVersionDisplay` and `effectivePluginsLibVersionDisplay`/`indicatedPluginsLibVersionDisplay`). No `v3.0.0` link is maintained — version is hash-based.
- **Update check** (`src/main.py:_is_update_available`, run at startup and on `POST /api/check-for-updates`): reads the stored `hash` (`_get_local_project_hash`) and compares it with the **hash asset of the latest release** (`_fetch_remote_project_hash` first fetches `https://github.com/LorenBll/Akupara/releases/latest/download/hash`, falling back to the raw `hash` file at the highest `vX.Y.Z` tag via `git ls-remote --tags origin` when the release has no asset yet). Different → an update is available; the settings page shows it and `AUTOMATIC_UPDATE` triggers `_perform_project_update` (git fetch + pull) and a restart. At startup with development off and still not on the latest release (auto-update off or failed), the local hash must additionally match a known release (`_is_known_release_hash`: latest asset, then the raw `hash` at each previous `vX.Y.Z` tag newest-first via `_fetch_release_hash_for_tag`) — no match → `log_error` + `error` sound and the process exits (`exit(1)`). `POST /api/check-for-updates` repeats these checks when development is off (integrity failure or unknown release → `exit(1)`); in development mode it returns `updateAvailable: false` without checking. The local integrity check and the update check are independent: the integrity check verifies the local files match the recorded hash, the update check compares the recorded hash with the latest release's hash asset.

## Plugins — list & library

- The **plugins-lib** folder is `resources/plugins-lib/`. Its catalog is split into **hash-range files** named `<low>-<high>.json` (64-char hex bounds, e.g. `000…-fff….json` while small). Each file holds a JSON **list** of plugin objects. A plugin has exactly `{"hash","name","description","repo","trust_mark"}` — no `reverse_index_keys` stored there and no duplication. `hash` is the ID, generated on insert as `SHA-256("name|description|repo|timestamp")` (`timestamp` is ISO-8601 UTC, `scripts/manage_plugin_library.py:generate_id_hash`).
- `reverse-index.json` is the **apposite file** `word -> [hash, …]` (lower-cased keys, `word` is `\w+` token for the research query). It is the *only* place `reverse_index_keys` live; hash-range entries never store them — `keys_for_hash(hash)` (`scripts/manage_plugin_library.py:keys_for_hash` / `src/plugin_bridge.py:_keys_for_hash`) computes them live from `reverse-index.json`.
- **Search** (`src/plugin_bridge.py:_search_plugins`, endpoint `POST /api/plugins/search`) tokenises the regex into `\w+` tokens, unions hashes from `reverse-index.json`, then regex-filters those candidates (case-insensitive on `name/description/repo` + JSON dump). If the index misses, it falls back to a full catalog regex scan. `reverse-index.json` therefore optimises research but does not change its semantics.
- **Folder integrity hash:** at any change, every file in `resources/plugins-lib/` *except* the apposite `hash` file (`resources/plugins-lib/hash`) is hashed individually (`SHA-256` hex), sorted by filename, concatenated and hashed again (`SHA-256`). Result is stored in `hash` (`scripts/manage_plugin_library.py:compute_plugins_lib_hash` / `src/plugin_bridge.py:_compute_plugins_lib_hash`). The public GPG key `resources/plugins-lib/lorenbll-akupara-pub` lives inside `plugins-lib` so it is hashed too. Splitting the library (`manage_plugin_library.py:action_split`) redistributes plugins into `n` equal hex intervals and rewrites all range files sorted by `hash`, then recomputes `hash`.
- **Loader startup** (`src/plugin_bridge.py:PluginBridge.start`, called immediately in `src/main.py:get_plugin_bridge().start()` after `_initialize_service_config`): (0) verifies the stored `hash` file's PGP signature (public key `resources/plugins-lib/lorenbll-akupara-pub`) — invalid/missing → `log_error` + `error` sound + **crash** (`exit(1)`); (1) recomputes the folder hash and compares it with the stored indicated hash — mismatch → **crash** (always, even in development); (2) if online, fetches the `hash` at the **latest commit** on the Akupara repository (`_fetch_latest_commit_sha` → `https://api.github.com/repos/LorenBll/Akupara/commits/main`, then `https://raw.githubusercontent.com/LorenBll/Akupara/<sha>/resources/plugins-lib/hash`) and compares the unsigned indicated hash with the unsigned remote hash directly — equal → nothing; different → `log_warn` update-available (auto-update driven by `AUTOMATIC_PLUGIN_LIBRARY_UPDATE`); offline → `log_warn` and falls back to the local checks. On success → `log_info Plugin loader started` and `is_started` true. Follows worker `start()/stop()` idempotency.
- **GPG prerequisite:** `gpg` (`GnuPG`, `C:\Program Files\GnuPG\bin` on Windows) must be on `PATH` for trust operations — signing (`gpg --armor --detach-sign`) and verification (`gpg --verify`).
- **Installed plugins discovery & upgrades** (`src/plugin_bridge.py:PluginBridge.discover_installed_plugins(development, auto_upgrade)`, returns `(verified, pending)`): checks every installed non-`dev-*` plugin (trust → folder hash → installed-version release hash → latest release hash → `akupara_version` gate); `dev-*` folders skip all checks and load only in development mode. `auto_upgrade=None` follows `AUTOMATIC_PLUGIN_UPGRADE`, `True` always upgrades, `False` only checks. At startup discovery runs with the setting (upgrades applied only when on; otherwise pending upgrades are cached in `_INSTALLED_PLUGINS_PENDING_UPGRADES` so the settings page renders `Update All`). Manual checks (`POST /api/check-for-plugin-upgrades`, `admin_session_authenticated`, always check-only) never upgrade independently of the setting; `POST /api/upgrade-all-plugins` (network callable, `admin_session_authenticated`) forces the upgrade of every pending plugin. Settings UI: `Installed Plugins Version` section with `checkForPluginUpgradesBtn` (`Check for Updates` ↔ `Update All`) and an installed-plugins table (`installedPluginsTable`: every plugin incl. `dev-*`, with library-resolved name, effective/indicated hashes blank for `dev-*`, per-row `Update` text button (disabled for `dev-*`) and trash `Delete`). Per-row operations go through `GET /api/installed-plugins` (list) and `/api/installed-plugins/<folder>` (`POST` upgrades only that plugin via `only_hash`, `DELETE` stops/deletes the folder with the standard row-deletion animation; network callable, `admin_session_authenticated`).

## Hash discrepancy behavior

The different actions taken when the **effective hash** (recomputed from local files) differs from the **indicated hash** (hash file) are intentional and derive from how the two hashes are generated and what they represent. Whenever a local hash is recomputed, it is checked against the indicated hash of the same kind before any update check; if the check fails the update check is skipped.

### Plugin library hash

The plugin library hash is **recomputed whenever the plugin library changes**. Therefore, if the effective hash differs from the indicated hash, the library has been modified in a way that is not expected or not yet certified. A mismatch must be treated as significant **even in development mode** (`resources/configuration.json:development` has no effect).

The Akupara developer is responsible for the public, authoritative hash of the plugin library and must retain authority over which version is considered valid and can be executed by the bridge after being obtained from the library. If validation were skipped in development mode, any locally modified or uncertified version could be considered valid, which would undermine this authority.

For this reason: the plugin library's **local hash validation is always mandatory** — the stored `hash` file must be validly signed, and the effective hash must always equal the indicated hash, regardless of development mode; a mismatch is an unexpected modification and crashes the process. The **remote** check (indicated vs the hash at the latest commit) is not a validity gate: it only decides whether an update is available — equal → nothing, different → automatic update when `AUTOMATIC_PLUGIN_LIBRARY_UPDATE` is on, otherwise a warning of update availability. Offline → the remote check is skipped with a warning.

Implementation: `src/plugin_bridge.py:_compute_plugins_lib_hash` / `src/main.py:_get_effective_plugins_lib_version` vs `plugin_bridge._read_stored_hash` / `src/main.py:_get_indicated_plugins_lib_version`; at startup `src/plugin_bridge.py:PluginBridge.start` verifies the stored hash's signature (`src/signing.py:read_signed_hash_file`) before any comparison — invalid signature → crash; then checks `effective vs indicated` — mismatch → crash; then (when online) compares `indicated` with the latest-commit hash via `plugin_bridge._fetch_remote_hash` — different → `log_warn` update-available. Separately, `effective`/`indicated` vs latest commit determines whether an update is available (`src/updates.py:_is_plugin_update_available`).

### Project hash

The project hash is computed **at each project release**, so the indicated hash represents the source code of a released version rather than every possible development-tree state. Therefore, in **development mode** (`development: true`) a mismatch is completely normal: a developer may have modified the source locally since the last release and the modified code should still be allowed to run. In **non-development mode** the same mismatch indicates an unexpected modification of the released source.

For this reason: the project's automatic update is **not mandatory in development mode** and may be skipped there; manual updates (`POST /api/update-now`) and the automatic-update toggle (`POST /api/automatic-update-enabled`) are refused in development mode (**403**); in development mode a mismatch is expected and should not prevent the modified project from running; in non-development mode a mismatch must be handled as an unexpected modification.

Implementation: `src/main.py:_compute_local_project_hash` / `_get_effective_project_version` vs `_get_local_project_hash` / `_get_indicated_project_version`; at startup `src/main.py:_verify_local_project_integrity` is checked before any update check — mismatch + `development: false` → `log_error` + `error` sound and the process exits (`exit(1)`, project does not start); mismatch + `development: true` → `log_warn` and the process continues. In **development mode** the project version check never happens: the startup update check is skipped (no remote hash is fetched) and `POST /api/check-for-updates` returns `updateAvailable: false` without fetching; `ui/pages/settings.html#checkForUpdatesBtn` (and the automatic-update toggle) is always rendered `disabled data-integrity-disabled` in development mode (title `Disabled in development mode`).

### Why the update policies are different

If project-hash validation and mandatory updating were handled identically to plugin-library validation in development mode, contributors could encounter: (1) **Their contribution could be reset** — a local modification causing `effective != indicated` would trigger an update that replaces their unreleased work; (2) **Their contribution could become impossible to run** — the project could refuse to execute solely because it differs from the latest release, even though that difference is expected during development. Neither is desirable. The plugin library is different because its validity must always be controlled by the developer, even during development.

### Why the plugin library uses the latest commit while the project uses the latest release

The plugin library uses the **latest commit** (`src/plugin_bridge.py:_fetch_latest_commit_sha` → `https://api.github.com/repos/LorenBll/Akupara/commits/main` + `https://raw.githubusercontent.com/.../<sha>/resources/plugins-lib/hash`) because a library change does not necessarily constitute a new application release and can be independently committed and certified without requiring a new release. The project uses the **latest release** (`src/main.py:_fetch_remote_project_hash` → `https://github.com/LorenBll/Akupara/releases/latest/download/hash`) because project changes are certified as part of a release. In short: **Plugin library → latest commit** (independently certifiable), **Project → latest release** (certified as part of a release).

## Trustworthiness mark

- For a plugin with `hash H`, the **trust data** is canonical JSON `{"hash":H,"name":…,"description":…,"repo":…,"reverse_index_keys":[…sorted]}` (`scripts/administration.py:build_trust_data` / `src/plugin_bridge.py:_build_trust_data` — `reverse_index_keys` computed live, never persisted). Canonicalisation is `json.dumps(sort_keys=True, separators=(",",":"))`.
- The Akupara developer signs that JSON with their **private GPG key** (`gpg --armor --detach-sign`). If `gpg` is unavailable, a deterministic `SHA-256` hex fallback is stored (warn).
- **Stored as single field** `trust_mark: string` (armored `-----BEGIN PGP SIGNATURE-----…` or `""` when absent) in the hash-range entry.
- **Public key** `resources/plugins-lib/lorenbll-akupara-pub` (armored) is distributed *inside* `plugins-lib` so it is covered by the folder hash. The private key is never committed.
- **Verification** (`src/plugin_bridge.py:verify_plugin_signature`): rebuilds trust data (including live `reverse_index_keys`), then if `trust_mark` is 64-hex → compares `SHA-256(canonical)`; else imports public key if needed and runs `gpg --verify sig data` (tries `gpg`, `C:\Program Files\GnuPG\bin\gpg.exe`). `""` / missing → `False`; tampered `name/description/repo/keys` → `False`. No piece of the signature is ever displayed by the manager (`scripts/manage_plugin_library.py:_print_plugin_card` shows only `[present]/[absent]`).

## Files that must not be committed

- `scripts/administration.py` — developer-only helper (project/plugin-library management: compute + GPG-sign the project hash, insert/list/delete/update/split plugins, plugin-library hashing and signing, `repo_exists` HTTP check). Runs via `scripts/administration.bat` / `.sh` wrappers (also not committed).
- `scripts/administration.bat` and `scripts/administration.sh` — functionally equivalent launchers (`python`/`python3` `3.10+` check, `.venv` create/activate, `pip install -r requirements.txt`, `exec python scripts/administration.py "$@"`).
- Private GPG key material (local keyring files, backups and any `*secret*.asc`) and `.env` (contains `USERS`/`API_KEYS` hashes). Public key `resources/plugins-lib/lorenbll-akupara-pub` **is** committed (hashed).

## Workflow

- **Hashes are generated manually and signed:** the project hash (repo-root `hash`) and the plugin-library hash (`resources/plugins-lib/hash`) are computed and GPG-signed by the developer via `scripts/administration.py` (menu: Project → Compute project hash; plugin-library actions sign `resources/plugins-lib/hash`). There is no CI that computes the hash on push.
- **Signed hash files:** both `hash` files carry the hash hex followed by an armored PGP signature (same key as plugin trust marks). At startup the runtime verifies the signature before comparing hashes — invalid signature → crash; plugin-library effective≠indicated → crash; project effective≠indicated → crash unless development mode.
- **Version is hash-based:** `Effective Version` / `Indicated Version` are `12-char` hashes (`_get_effective_*` / `_get_indicated_*`); no manual `v3.0.0` string is maintained in `ui/pages/settings.html`.
